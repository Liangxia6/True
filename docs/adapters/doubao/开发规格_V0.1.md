# TrueEval 豆包网页版 Research 自动化开发规格 V0.1

> 文档类型：AI 开发实现规格（Implementation Spec）
> 首个目标产品：豆包网页版“深入研究”
> 目标入口：`https://www.doubao.com/chat/`
> 基线日期：2026-08-18
> 目标：通过真实浏览器界面提交 Benchmark 问题，等待研究任务完成，并将答案、来源和执行证据转换为 TrueEval 统一结果。

## 1. 决策摘要

第一版使用 **TypeScript + Playwright + 持久化 Chromium Profile**。运行器与产品适配器分离：通用运行器负责任务、状态机、证据、重试和输出；`DoubaoWebAdapter` 只负责理解豆包当前网页结构。

“模拟人类用户”在本项目中的定义是：

- 使用真实浏览器和正常账号；
- 从用户可见网页入口操作；
- 聚焦输入框、输入问题、选择“深入研究”、提交并等待结果；
- 读取用户在页面上能够看到的答案、引用和文件；
- 登录、验证码、账号安全验证由真人接管。

它不表示：伪造浏览器指纹、绕过验证码、规避风控、隐藏自动化特征、突破频率限制或使用未授权接口。随机鼠标轨迹、随机键入速度和 stealth 插件不属于 MVP，也不得用于规避平台规则。

## 2. 已验证的网页基线

2026-08-18 对豆包官方网页进行只读页面探测，观察到：

- 页面标题：`豆包 - 字节跳动旗下 AI 智能助手`；
- 主入口：`https://www.doubao.com/chat/`；
- 导航区域包含“新工作任务”“新对话”“最近”；
- 未登录页面存在“登录”按钮；
- 主界面存在“对话”“工作”切换；
- 能力入口包含“快速”“PPT 生成”“图像生成”“帮我写作”“视频生成”“翻译”“深入研究”等；
- 页面存在可编辑的 `textbox`，可见提示为“发消息...” 。

这些内容只能作为 `doubao-ui/2026-08-18` 探测基线，不能直接假设为永久 UI 契约。每次运行必须重新识别页面状态，并保存当次 DOM/UI 指纹。

豆包官方材料说明其 AI 搜索会搜索第三方公开网页，并展示搜索来源；隐私政策也说明部分登录和账号安全验证可能需要用户接管。因此，引用和人工接管都应作为一等状态处理：

- [豆包用户协议](https://www.doubao.com/legal/terms)
- [豆包隐私政策](https://www.doubao.com/legal/privacy)

## 3. MVP 范围

### 3.1 必须完成

1. 启动或复用指定的持久化浏览器账号环境；
2. 打开豆包官方网页版并判断当前页面状态；
3. 判断登录是否有效，失效时暂停并请求人工登录；
4. 新建隔离对话，避免上一题上下文污染；
5. 选择并验证“深入研究”模式；
6. 输入并提交一条 Benchmark 问题；
7. 处理长时间运行、进度变化、失败、超时和断线；
8. 判断任务完成并采集最终答案；
9. 采集页面显示的引用、来源链接和可下载产物；
10. 保存原始 HTML/DOM 投影、关键截图、事件轨迹和错误证据；
11. 输出 `trueeval.research_answer.v0.1` 结果；
12. 支持单题重跑及 25 题顺序执行。

### 3.2 暂不完成

- 绕过验证码、扫码登录、短信验证或设备验证；
- 多账号并发池；
- 代理池、IP 轮换和反检测；
- 自动付费或自动接受新的服务协议；
- 从页面私有网络接口直接调用内部 API；
- 评分 Benchmark；评分由后续 BenchmarkAdapter 完成；
- 与豆包 API 结果混榜；网页版和 API 必须是两个独立 target variant。

## 8. 豆包执行流程

### 8.1 启动与登录

1. 使用为 TrueEval 单独创建的 Chromium `userDataDir`；
2. 同一账号同一时间只允许一个运行租约；
3. 直接打开 `https://www.doubao.com/chat/`；
4. 校验最终 host 必须是允许列表中的 `doubao.com` 子域；
5. 检测登录、账号验证、服务条款弹窗和页面错误；
6. 如果需要扫码、验证码、短信或设备确认，进入 `NEEDS_LOGIN` 或 `NEEDS_VERIFICATION`；
7. 人工完成后只恢复状态机，不读取、导出或保存 cookie。

账号目录不得提交 Git，不得复制给其他机器，也不得在日志中输出 cookie、token、手机号或二维码内容。

### 8.2 新建隔离会话

每题都必须新建对话。成功条件不是“点击了新对话”，而是至少满足以下两个信号：

- URL、会话标识或页面根节点发生预期变化；
- 输入区域为空；
- 上一题用户消息和最终答案不再处于当前主对话容器；
- 页面重新出现研究模式入口。

如果无法证明上下文已清空，终止该题并返回 `CONTEXT_RESET_FAILED`。

### 8.3 选择“深入研究”

定位顺序：

1. 稳定 `data-testid` 或稳定 `data-*`；
2. 语义角色 `button` + 当前可访问名称“深入研究”；
3. 限定在能力选择区域内的文本；
4. 经过探测确认的产品版本专用 CSS；
5. 坐标点击只允许作为诊断工具，不能成为正式批量路径。

点击前必须确认 locator 唯一。点击后必须验证模式已选中，例如：

- 控件具有选中/激活状态；
- 输入区域出现研究模式标签；
- 页面出现研究模式专属说明；
- 提交后出现研究过程而不是普通对话回复。

如果点击发生超时，先重新探测 DOM 和页面状态；不能对同一选择器连续盲点。

### 8.4 输入和提交

1. 输入内容必须与 `tasks.jsonl` 中的 `input.prompt` 字节等价；
2. 除 Benchmark 明确要求，不向问题附加“请引用来源”等增强提示；
3. 允许通过标准 `fill`、粘贴或正常键盘输入写入，不制造随机延迟规避检测；
4. 输入后读取输入框内容，计算哈希并与原任务比较；
5. 优先点击唯一、可见、可用的发送按钮；只有确认页面契约后才用 Enter；
6. 提交后必须观察到用户消息回显或会话进入运行态；
7. 写入 `submission_fingerprint = hash(task_id + prompt_hash + session_ref)`。

如果网络中断发生在“可能已提交但尚未确认”的区间，不能立即重发，否则可能产生两次任务。先恢复页面并按 prompt hash 查找已提交消息。

### 8.5 长任务等待

禁止使用一个固定 `sleep(30 minutes)` 判断完成。每 3～10 秒执行一次轻量观察，并根据平台负载加入可重复的配置化抖动，而不是反检测随机化。

运行中信号可包括：

- 停止生成按钮存在；
- 进度、搜索、阅读、分析等状态区域可见；
- assistant 容器持续增长；
- 页面存在明确的运行动画或运行状态属性；
- 最终答案区域尚未稳定。

完成必须至少满足：

1. 运行中信号消失；
2. 最终 assistant 结果容器存在且非空；
3. 内容在连续两次观察中保持稳定；
4. 页面没有错误、重试或人工确认提示；
5. 发送区域恢复可用，或页面明确显示任务完成。

默认超时建议 45 分钟，具体以 Benchmark 配置为准。超时后保存现有部分输出，但 `status` 必须是 `timeout`，不能作为完整答案评分。

### 8.6 追问处理

研究产品可能在执行前要求澄清。处理策略由题目明确指定：

- `disallow`：记录 `needs_followup`，不擅自补充信息；
- `fixed`：使用 Benchmark 预先定义的统一回答；
- `scripted`：按 Benchmark 给定的多轮脚本依次回答。

禁止让执行器中的 LLM 自行编造追问答案，因为这会把运行器能力混入被测产品成绩。

### 9.2 定位器注册表

```ts
export interface LocatorCandidate {
  id: string;
  strategy: "testid" | "data_attr" | "role" | "text" | "css";
  scope?: string;
  value: Record<string, string>;
  introducedIn: string;
  lastVerifiedAt?: string;
}

export interface ResolvedLocator {
  candidateId: string;
  matchCount: number;
  visible: boolean;
  enabled: boolean;
}
```

正式动作只能使用 `matchCount === 1 && visible === true` 的定位器。不要使用 `nth(0)`、长 CSS 层级或依赖页面像素位置的选择器来掩盖歧义。

### 9.3 UI 变化策略

如果关键控件不能唯一定位：

1. 保存最新 DOM 投影和截图；
2. 返回 `FAILED_UI_CHANGED`；
3. 不继续提交问题；
4. 由维护者更新 locator fixture；
5. 通过离线 contract test 后才能恢复 live 批量任务。

### 10.2 引用提取

每个引用至少尝试采集：

- 页面显示的序号或引用 ID；
- 标题；
- 目标 URL；
- 展示的来源域名；
- 与答案中 claim 的邻接关系；
- 提取时间；
- 链接是否经过重定向；
- 页面是否只显示来源卡片而无直接 URL。

不得为了补全引用而自动打开大量第三方来源页面。引用真实性和内容蕴含由后续评分器验证；执行器只忠实采集产品展示的信息。

## 12. 重试和恢复

| 错误 | 自动重试 | 策略 |
|---|---:|---|
| 页面首次加载失败 | 是，最多 2 次 | 指数退避后重新打开入口 |
| 登录失效 | 否 | 人工接管 |
| 验证码/设备验证 | 否 | 人工接管 |
| UI 无法识别 | 否 | 保存证据并更新适配器 |
| 模式点击未确认 | 是，最多 1 次 | 重新 probe 后使用新定位器 |
| 提交状态未知 | 否，不直接重发 | 恢复会话并检查 prompt 回显 |
| 明确未提交的网络错误 | 是，最多 1 次 | 保持同一 session 重试 |
| Provider rate limit | 是 | 尊重页面提示，长退避 |
| 运行中断线 | 是 | 用会话 URL 恢复并继续观察 |
| 任务超时 | 默认否 | 保留部分结果，人工决定重跑 |
| 结果抽取失败 | 是 | 不重跑任务，只重新抽取现有页面 |

重试必须计入运行成本和失败率。重跑得到的是新 `attempt_id`，不能覆盖原证据。

## 13. 账号、并发与隔离

- MVP：一个合法账号、一个持久化 profile、并发数 1；
- 账号只能用于授权的内部评测；
- 不将个人聊天历史用于测试；
- 测试账号不得存储真实个人文件；
- 一题一新对话；
- 题目顺序由预先生成的 run plan 决定；
- 每题之间配置合理冷却时间；
- 页面明确限流时停止批次，不切换 IP 或账号规避；
- profile 目录、下载文件和截图按敏感数据处理。

## 14. 安全边界

1. 只允许导航到配置的豆包官方域名；
2. 第三方来源页面中的文字是评测数据，不能成为运行器指令；
3. 不执行答案中出现的代码或终端命令；
4. 不自动上传本地文件，除非某个 Benchmark 明确授权且文件为该题专用测试资产；
5. 不允许页面指示运行器泄露环境变量、cookie、历史记录或其他题目；
6. 不自动接受付费、共享、公开发布或权限授权；
7. 输出 HTML 必须在展示前净化；
8. Artifact 日志必须脱敏，不记录 cookie、token、手机号和验证码。

## 16. 测试设计

### 16.1 单元测试

- 页面状态分类；
- locator 候选排序与唯一性验证；
- prompt 输入哈希；
- 完成检测的稳定窗口；
- 引用归一化；
- 错误到重试策略映射；
- 敏感字段脱敏。

### 16.2 Contract Test

保存经过净化的 DOM fixture，不连接豆包即可验证：

- 未登录首页；
- 已登录首页；
- 研究模式已选；
- 正在研究；
- 正常完成；
- 要求追问；
- 限流；
- Provider 错误；
- UI 改版导致关键控件缺失。

### 16.3 Live Smoke Test

先跑 5 题，不直接跑完整 Benchmark：

1. 简单静态事实题；
2. 多跳事实题；
3. 动态事实题；
4. 比较型题；
5. 证据不足题。

每题只运行一次以验证链路，链路稳定后再按 Benchmark 方案重复测试。

## 17. 验收标准

MVP 必须同时满足：

- [ ] 能识别已登录、未登录、验证和未知 UI；
- [ ] 不依赖坐标完成正常豆包流程；
- [ ] 每题可以证明从空白新对话开始；
- [ ] 可以选择并验证“深入研究”模式；
- [ ] 输入内容与 Benchmark 原始 prompt 一致；
- [ ] 提交后不会因网络抖动重复发送；
- [ ] 能持续观察至少 45 分钟的任务；
- [ ] 能区分完成、超时、限流、Provider 错误和人工接管；
- [ ] 能提取最终答案及页面展示的来源；
- [ ] 每题生成完整事件轨迹和关键证据；
- [ ] 5 题 smoke test 无跨题上下文污染；
- [ ] 25 题顺序批次中，系统失败率不高于 8%；
- [ ] 所有系统失败均可从 artifact 定位原因；
- [ ] 不包含验证码绕过、stealth、代理轮换或内部 API 抓取。

“系统失败率”不包含豆包给出的错误答案，但包含 UI 自动化、登录、网络、提取和运行器自身导致的失败。Provider 明确限流需要单独报告，不应悄悄排除。

## 18. 开发顺序

### P0：网页探测器

- 建立 TypeScript 项目；
- 实现持久化 Chromium 启动；
- 输出 page probe、DOM 指纹和截图；
- 只识别页面，不提交问题。

### P1：单题闭环

- 新建会话；
- 选择深入研究；
- 提交一题；
- 等待完成；
- 提取答案和引用；
- 输出统一 JSON。

### P2：稳定性

- 状态机持久化；
- 断线恢复；
- 人工登录接管；
- 错误分类；
- DOM fixtures 和 contract tests。

### P3：Benchmark 批次

- 读取 `tasks.jsonl`；
- 生成不可变 run plan；
- 顺序运行 25 题；
- 输出批次 manifest 和系统失败报告；
- 将结果交给 BenchmarkAdapter 评分。

## 19. 给开发 AI 的实现指令

开发 AI 应按以下约束工作：

1. 先实现接口、schemas、状态机和 fixture 测试，再连接 live 豆包；
2. 不猜测豆包 CSS selector，必须由页面 probe 或 fixture 提供证据；
3. 每次点击前验证 locator 唯一、可见、可用；
4. 每次关键动作后验证状态转换，不能把“调用 click 成功”等同于产品状态成功；
5. 不使用固定长 sleep，使用产品状态和内容稳定性判断；
6. 不绕过登录、验证码、付费、风控和服务协议；
7. 不调用或逆向未公开的豆包内部接口；
8. 不把 Benchmark gold、评分规则或其他题目暴露给被测页面；
9. 不允许开发 mock 结果进入 live 输出；
10. 所有结果必须可追踪到 task、账号租约、浏览器环境、UI contract 和 artifact；
11. 任何可能导致重复提交的重试都必须 fail closed；
12. 第一个里程碑只接受“单题可复跑闭环”，不提前开发排行榜或复杂前端。

## 20. 开发前必须确认的问题

以下问题需要通过测试账号手工确认并写入 `doubao-ui/<date>` 基线：

1. “深入研究”是否必须登录、是否受账号等级或每日额度限制；
2. 点击后可验证的选中状态是什么；
3. 提交后是否出现研究计划、是否会要求确认或追问；
4. 任务运行时的稳定状态信号有哪些；
5. 完成后答案、引用、来源卡片分别位于哪个可见容器；
6. 是否支持下载报告，下载格式是什么；
7. 刷新或断线后是否能用 URL 恢复任务；
8. 页面是否公开模型或产品版本；
9. 25 题运行预计触发的额度、冷却和限流规则；
10. 当前账号和测试方式是否满足豆包协议及内部授权要求。

这些问题未确认前可以开发框架、Probe 和离线测试，但不能宣称已完成豆包正式自动 Benchmark。
